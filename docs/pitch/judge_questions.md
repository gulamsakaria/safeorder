# Likely judge questions, with honest answers

> **DRAFT for the team to review. Not legal advice, not an upay policy, not a product.**
> Synthetic data, simulated money, not validated on real data.
> Generated by `scripts/build_pitch.py`; edit the script (or copy the text out) rather than this file.

**Is this validated on real data?**

No. Everything is synthetic and the system says so on every screen. The numbers show that the pipeline works and how it behaves on a different generator; real validation would need governed, anonymised data.

**Who wrote the dispute cases? ChatGPT? Real customers?**

An AI assistant wrote them, not ChatGPT or Gemini and not the team, and nobody has reviewed them. All splits share that one author, so scores are optimistic for other people's text. Test 2 has 28 distinct stories in 244 cases; scored one per story, macro-F1 is 0.58. The pipeline accepts team-written cases (`raw/team_*.jsonl`) and reports them separately.

**Why should we trust the trust score?**

On a held-out generator it finds 88% of high-risk sellers at 5% false alarms against 35% for ranking by account age. But the generator is our own assumptions, so it proves the model can learn those behaviours, not that real fraud looks like that.

**Does it treat new honest sellers unfairly?**

New accounts get a neutral limited-history band, not a low score. Taken literally the blueprint rule would hide every fake seller too (recall 54%), so a score at or below 20 is still shown as high risk (recall 98%); honest new sellers wrongly flagged: 1.0%. That threshold is a policy choice for people to confirm.

**Can prompt injection fool the analyzer?**

The screen is a first filter, not a defence: it caught 22 of 22 phrases it was built on but 1 of 12 written afterwards, and 8 of 24 injected cases in the classifier test. The protection that holds is structural: no text changes a label, a route or a ledger entry, no generative model is in the decision path, and a detected injection forces human review. A missed phrase reaches a bag-of-words model as ordinary words.

**What stops it refunding a false claim?**

A person confirms every refund. The classifier would suggest a refund for 5.3% (test 1) and 8.5% (test 2) of false claims, so flags (code used, repeat claimant), a confidence threshold (0.80) and an amount threshold (5000 taka) send most cases to a human. In the fast lane, 0 wrong refunds on test 1 (that is on synthetic text).

**Why not use a large language model?**

A generative model in the decision path is hard to audit, can be steered by the very text it reads, and the guideline asks to keep rules and predictions apart. A small model plus rules is explainable, fast (5.3 ms per dispute) and runs privately.

**Did you use a transformer?**

No. It was optional; trained on one author's cases it would mostly learn the templates better, and a Bangla base model needs a licence check. It stays behind a config flag for later.

**What does the money hold mean legally?**

Holding customer funds may need approval from the financial regulator and upay. We present it as a future upay-governed feature, simulated here; see `docs/drafts/regulatory_note.md`.

**What happens to photos and videos?**

Not read by ML. Evidence is described in text. A perceptual-hash duplicate check is on the roadmap.

**Can a seller game the score?**

Collusion rings are in the data and the model sees shared-buyer overlap, but a determined attacker adapts. The roadmap has graph methods; humans review every dispute.

**How much loss does it prevent? How many minutes does it save?**

Not measured: no real data and no timed analyst sessions (not measured). We can show what is measured and how a pilot would measure the rest.

**How would this scale?**

Events in (order, courier update, wallet movement, dispute), the existing ledger and state machine, governed data for a validation stage, monitoring for drift and outcomes, and review service levels. We need from upay: governed data access for validation and an integration contact.

**What if my live case confuses it?**

It may be wrong on unseen text: low confidence goes to a human, which is the design. Insufficient evidence is the weakest class.

**Is the live demo real?**

The data is synthetic and the money simulated, but the models are the real trained ones, the same files that are in the repository and on Kaggle. Accounts, held payments, the 24-hour and 72-hour timers, disputes and the admin area all run on the server code in this repository.

**Where does it run? Where is the model deployed?**

The models are trained in Python (files in models/, copies on Kaggle) and loaded by the API, a FastAPI service. A hosted copy is the static website on our sub-domain calling that API on a free Render server with a Postgres database. Anyone can also run all of it on their own computer with one command (python run_local.py), or with Docker; the README explains both. The free server sleeps when idle, so the first request after a pause is slow.
